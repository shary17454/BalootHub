# لمّة بلوت (Baloot Hub)

تطبيق iPhone عربي (RTL) يجمع ألعاب البلوت وأنماطها، أدوات البلوت، وألعاب ورق شعبية أخرى في مكان واحد،
مع محرك لعب بلوت محلي أولي ضد لاعبين آليين، وأداة مستقلة كاملة لتسجيل نقاط البلوت. يعمل بالكامل دون
اتصال بالإنترنت، ولا يحتوي تسجيل دخول أو مشتريات أو إعلانات أو تتبّع.

## المتطلبات

- Xcode 16 أو أحدث (تم التطوير والاختبار على Xcode 26.4.1 / Swift 6.3.1).
- iOS 17.0 فأعلى (iPhone فقط، بدون دعم iPad في هذا الإصدار).
- لا حاجة لأي حساب أو مفتاح API أو اتصال شبكة.

## التشغيل في Xcode

```bash
open BalootHub.xcodeproj
```

1. اختر Scheme باسم **BalootHub** ومحاكي iPhone (مثل iPhone 17).
2. شغّل بـ ⌘R، أو نفّذ الاختبارات بـ ⌘U.
3. عند أول تشغيل، يُزرع كتالوج الألعاب تلقائيًا داخل قاعدة بيانات SwiftData محلية على الجهاز.

من سطر الأوامر:

```bash
xcodebuild build -scheme "BalootHub" -destination "platform=iOS Simulator,name=iPhone 17"
xcodebuild test  -scheme "BalootHub" -destination "platform=iOS Simulator,name=iPhone 17"
```

اختبارات محرك البلوت (حزمة Swift مستقلة، لا تحتاج Xcode):

```bash
cd Packages/BalootEngine && swift test
```

## Xcode Cloud

يحتوي المستودع مجلد [`ci_scripts/`](ci_scripts/) بجانب `BalootHub.xcodeproj` مباشرة (المكان الذي يشترطه Apple).
السكربت الوحيد حاليًا هو `ci_post_clone.sh`: يعمل بعد استنساخ المستودع وقبل حل اعتماديات SPM، ويسجّل نسخة
Xcode/Swift المستخدمة في بيئة البناء السحابية، ويتحقق من وجود حزمة `Packages/BalootEngine` قبل المتابعة حتى
تظهر أي مشكلة بنية بوضوح في السجلّ بدل فشل غامض لاحقًا. لم تُضف سكربتات `ci_pre_xcodebuild.sh` أو
`ci_post_xcodebuild.sh` لأنه لا يوجد لهما عمل فعلي بعد (لا تنبيهات خارجية ولا خطوات ما بعد بناء مطلوبة حاليًا).

تفعيل Xcode Cloud نفسه (Product → Xcode Cloud → Create Workflow) خطوة تفاعلية داخل Xcode تتطلب حساب Apple
Developer الخاص بك، ولا يمكن لأداة آلية أن تقوم بها نيابة عنك.

## بنية المشروع

```
BalootHub/
├── BalootHub.xcodeproj/        مشروع Xcode (Target تطبيق + Target اختبارات)
├── BalootHub/                  هدف التطبيق
│   ├── App/                    نقطة الدخول، التوجيه (Router)، حالة التنقل المشتركة
│   ├── Core/
│   │   ├── DesignSystem/       الألوان والمسافات والخطوط والظلال والحركة + مكوّنات مشتركة
│   │   └── Persistence/        إعداد SwiftData وزرع الكتالوج الأولي
│   ├── Domain/
│   │   ├── Models/              نماذج SwiftData (الكتالوج، الجلسات، الجولات، الإعدادات)
│   │   ├── Repositories/        الوصول لبيانات الإعدادات
│   │   └── Services/            منطق أعمال خالص وقابل للاختبار (فلترة الكتالوج، قواعد التسجيل)
│   └── Features/                كل شاشة في مجلدها: Home, Catalog, GameDetails, Rules,
│                                 Scorekeeper, MatchHistory, BalootGame, Settings
├── BalootHubTests/              اختبارات وحدة على مستوى التطبيق (XCTest)
├── Packages/BalootEngine/       حزمة Swift محلية: محرك لعب البلوت الكامل (بلا SwiftUI)
│   ├── Sources/BalootEngine/    الأوراق، الحالة، القواعد، التحقق، الاحتساب، اللاعب الآلي
│   └── Tests/BalootEngineTests/ اختبارات المحرك (Swift Testing)
└── README.md
```

هذه البنية أقرب ما يمكن لما طُلب في BLUEPRINT الأصلي، مع تبسيط بسيط: منطق البلوت (الأوراق/القواعد/الاحتساب/اللاعب
الآلي) وُضع في حزمة Swift محلية مستقلة (`Packages/BalootEngine`) بدل مجلد `GameEngine/` داخل هدف التطبيق مباشرة،
لأن ذلك يجعله:
- قابلاً للاختبار عبر `swift test` دون الحاجة لبناء تطبيق iOS كامل أو محاكي.
- معزولاً فعليًا عن SwiftUI (لا يستورد أي شيء من `SwiftUI` أو `SwiftData`)، وهو ما طلبته التعليمات صراحة.
- جاهزًا لإعادة استخدامه لاحقًا في خادم أو محرك لعب جماعي دون أي تغيير.

## إضافة لعبة أو نمط جديد إلى الكتالوج

كل بطاقات الرئيسية والألعاب تُبنى من نموذج بيانات واحد (`GameCatalogItem` + `GameRuleSection`) دون أي شرط
`if`/`switch` خاص بكل لعبة في الشاشات نفسها. لإضافة لعبة جديدة:

1. افتح [`CatalogSeeder.swift`](BalootHub/Core/Persistence/CatalogSeeder.swift).
2. أضف عنصر `GameDefinition` جديدًا في `allDefinitions` (الاسم، التصنيف، الوصف، عدد اللاعبين، الصعوبة،
   المدة، الأيقونة، وهل هي قابلة للعب).
3. املأ الأقسام العشرة لقواعد اللعبة (`StandardRuleSectionKind`) بمحتوى عربي أصلي.
4. هذا كل شيء — البطاقة ستظهر تلقائيًا في القسم الصحيح بالرئيسية، وفي شبكة صفحة الألعاب، وفي نتائج البحث
   والفلاتر، وستُبنى صفحة التفاصيل والقواعد الخاصة بها تلقائيًا.

> ملاحظة: الكتالوج يُزرع مرة واحدة فقط عند أول تشغيل (`CatalogSeeder.seedIfNeeded`). لرؤية عناصر جديدة أثناء
> التطوير، احذف التطبيق من المحاكي أولًا لمسح قاعدة البيانات المحلية القديمة.

## تصنيف المحتوى

- **ألعاب البلوت**: بلوت كلاسيكي، بلوت صن، بلوت حكم، بلوت مشاريع، بلوت دبل — هذه كلها أنماط/قواعد ضمن لعبة
  البلوت نفسها، وليست ألعابًا منفصلة.
- **أدوات البلوت**: بلوت تدريب، تحدي حساب النقاط، تسجيل البلوت — أدوات مساعدة، ليست جولات لعب تنافسية.
- **ألعاب ورق أخرى**: كوت بو ستة، طرنيب، تركس، هاند — ألعاب ورق شعبية مستقلة تمامًا عن البلوت.

## قواعد البلوت الافتراضية المستخدمة في المحرك

بعض تفاصيل قواعد البلوت مختلف عليها بين المجالس، فاختار هذا التطبيق إعدادًا افتراضيًا موثّقًا وقابلاً للتهيئة
عبر `BalootRulesConfiguration` (محرك اللعب) و`ScoreRules`/`ScoreRulePreset` (مسجّل النقاط):

| القاعدة | الافتراضي المستخدم |
|---|---|
| ترتيب أوراق نمط حكم (نوع الحكم) | الشايب (J) أعلى، ثم 9، A، 10، K، Q، 8، 7 |
| ترتيب أوراق نمط حكم (الأنواع الأخرى) ونمط صن | A أعلى، ثم 10، K، Q، J، 9، 8، 7 |
| مجموع نقاط جولة حكم | 152 (لا تُضاف مكافأة أخرى) |
| مجموع نقاط جولة صن الأساسي | 130 (120 من الأوراق + 10 لآخر أكلة) |
| مضاعف احتساب صن ضمن هدف المباراة | ×2 (فتصبح 260) — `sunScoreMultiplier` |
| الإلزام بالقطع بالحكم عند عدم توفر النوع | مفعّل افتراضيًا — `mustTrumpWhenVoid` |
| الإلزام بالتعلية (حكم أعلى من المطروح) | غير مفعّل افتراضيًا — `mustOvertrump` |
| المشروع المعتمد في المحرك | "البلوت" فقط (شايب + بنت الحكم) = 20 نقطة |
| مضاعفات تسجيل البلوت (دبل/ثري/فور) | ×2 / ×3 / ×4 افتراضيًا — Preset "الصيغة القياسية" |
| مضاعف "قهوة" | ×4، ومعطّل افتراضيًا حتى يُفعَّل من الإعدادات |
| الحد المستهدف الافتراضي لجلسة التسجيل | 152 نقطة، وقابل للتخصيص لكل جلسة |

## الاختلافات القابلة للتهيئة

- **`BalootRulesConfiguration`** (`Packages/BalootEngine/Sources/BalootEngine/Rules/`): مجموع نقاط حكم/صن،
  مكافأة آخر أكلة، الإلزام بالقطع، الإلزام بالتعلية.
- **`ScoreRules` / `ScoreRulePreset`** (`BalootHub/Domain/Services/ScoreRules.swift`): عاملا الدبل/الثري/الفور،
  عامل القهوة، وهل القهوة مفعّلة أصلًا — تُختار من شاشة الإعدادات ولا تُثبَّت داخل أي View.
- **`AppSettings`**: الحد المستهدف الافتراضي، تفعيل القهوة، التأكيد قبل الحذف/التراجع، المظهر، الصوت،
  الاهتزاز.

## الاختبارات المنفذة فعليًا

- **`Packages/BalootEngine/Tests/BalootEngineTests`** (Swift Testing، 21 اختبارًا): الحزمة والتوزيع، ترتيب
  الأوراق، التحقق من الحركات القانونية (التلزيم والقطع)، تحديد الفائز باللمة، احتساب النقاط الكامل لجولة
  صن (يجب أن يساوي 260)، احتساب مشروع البلوت، منع اللعب خارج الدور، رفض حركة غير قانونية، إعادة التشغيل من
  سجل الأفعال، وأن اللاعب الآلي يختار دائمًا ورقة قانونية.
- **`BalootHubTests`** (XCTest، 25 اختبارًا): صيغة احتساب مضاعفات التسجيل (`ScoreRulesTests`)، إجمالي
  الجلسة والفريق المتقدم وإعلان الفائز والتراجع وتقييد القيم السالبة (`ScoreSessionTests`)، بحث وفلترة
  الكتالوج والتأكد من اكتمال كل الأقسام العشرة لكل لعبة (`CatalogFilterTests`)، وزرع الكتالوج مرة واحدة فقط
  وإنشاء سجل إعدادات وحيد (`CatalogSeederTests`) عبر SwiftData داخل الذاكرة.
- **إجمالي: 46 اختبارًا، كلها ناجحة فعليًا** (نتائج التشغيل الفعلية في التقرير النهائي أدناه).

## البيانات المحلية المستخدمة (خصوصية)

كل البيانات تُخزَّن محليًا على الجهاز فقط عبر SwiftData، ولا تُرسَل لأي خادم:

- كتالوج الألعاب وحالة المفضلة لكل لعبة.
- جلسات تسجيل البلوت وجولاتها (أسماء الفرق، النقاط، المشاريع، المضاعفات، الملاحظات، التواريخ).
- إعدادات التطبيق (المظهر، الصوت، الاهتزاز، الحد المستهدف، صيغة المضاعفات، تأكيد الحذف).

لا يطلب التطبيق أي صلاحية للوصول للصور أو جهات الاتصال أو الموقع، ولا يحتوي أي SDK تحليلات أو تتبّع، ولا
يفتح أي اتصال شبكة. لم تتم إضافة `PrivacyInfo.xcprivacy` لأن التطبيق لا يستخدم أي "Required Reason API"
(مثل قراءة الطوابع الزمنية للملفات أو `UserDefaults` أو مساحة التخزين) تستوجب تصريح خصوصية حسب سياسة Apple
الحالية؛ إن أُضيفت مكتبة أو API من هذا النوع لاحقًا يجب إضافة الملف حينها.

## الميزات غير المكتملة (بصراحة)

- **لعبة بلوت مشاريع / بلوت دبل**: صفحتا قواعد فقط (`isPlayable = false`) — محرك اللعب الحالي يدعم مشروع
  "البلوت" فقط، ولا يدعم مزايدة الدبل التفاعلية (دبل/ثري/فور) أثناء اللعب الفعلي، ولا مشاريع السرا/الخمسين/
  المية. القيم والمنطق موجودان جزئيًا في `Multiplier`/`Project` لكنهما غير مفعّلين بالكامل في تدفق اللعب.
- **تحدي حساب النقاط**: صفحة مرجعية تشرح الاحتساب، وليست اختبارًا تفاعليًا (كويز) فعليًا بعد.
- **بلوت تدريب**: يعيد استخدام قالب صفحة القواعد نفسه بمحتوى تعليمي، وليس شاشة تفاعلية منفصلة بخطوات
  متسلسلة.
- **بيدنغ (المزايدة) في اللعب الفعلي**: مبسّطة لدور واحد يختار فيه اللاعب صن أو حكم مباشرة، دون دورة مزايدة
  تنافسية كاملة بين الأربعة لاعبين.
- **Strict Concurrency**: مفعّلة بالكامل (Swift 6 Language Mode) في حزمة `BalootEngine`، لكن هدف التطبيق
  نفسه يبني بوضع Swift 5 لتقليل مخاطر تعارضات الفحص الصارم عبر عشرات ملفات SwiftUI في هذه الجولة الأولى.
- **صور/رسومات مخصصة لكل لعبة**: تُستخدم SF Symbols فقط حاليًا بدل رسوم توضيحية أصلية لكل لعبة.
- **تحقق UI تفاعلي كامل عبر المحاكي**: البناء والاختبارات الآلية نجحت فعليًا (انظر التقرير)، وأُخذت لقطة شاشة
  فعلية للصفحة الرئيسية تؤكد صحة RTL والعربية، لكن جولة تفاعلية كاملة (ضغط كل زر يدويًا) لم تُنفَّذ لعدم منح
  صلاحية التحكم بالمحاكي لهذه الجلسة.
