# البلوت (Baloot Hub)

تطبيق iPhone عربي (RTL بشكل أساسي، مع دعم كامل للإنجليزية) يجمع ألعاب البلوت وأنماطها، أدوات البلوت،
وألعاب ورق شعبية أخرى في مكان واحد، مع محرك لعب بلوت محلي ضد ذكاء اصطناعي أو أربعة أشخاص على نفس الجهاز، وأداة مستقلة كاملة
لتسجيل نقاط البلوت. يعمل بالكامل دون اتصال بالإنترنت، ولا يحتوي تسجيل دخول ولا إعلانات ولا تتبّع.
النسخة الحالية مجانية بالكامل ولا تحتوي بوابة شراء داخل التطبيق.

## اللغات المدعومة

العربية هي لغة المصدر، والتطبيق يدعم **11 لغة** عبر String Catalog
(`Resources/Localizable.xcstrings`) مع تبديل تلقائي للاتجاه (RTL/LTR) حسب لغة الجهاز — لا يوجد فرض للغة
أو الاتجاه في الكود.

**تغطية الترجمة الفعلية** (تُحدَّث مع كل دفعة، والمصدر المعتمد هو ملف الكتالوج نفسه لا هذا الجدول):

| اللغة | الواجهة | محتوى الكتالوج (الأوصاف والقواعد) |
|---|---|---|
| العربية (المصدر) | ✅ 1442 نصًا | ✅ |
| الإنجليزية | ✅ 1402 نصًا | ✅ |
| الفرنسية · الإسبانية · الألمانية · التركية · الروسية · الأردية · الهندية · الإندونيسية · الصينية المبسّطة | ✅ 1264 نصًا لكل لغة | ⚠️ يرجع للعربية |

> **كل نص تستخدمه الواجهة فعلًا صار مترجمًا للعشر لغات** (ارتفعت التغطية من 555 إلى 1264 نصًا لكل لغة).
> الفرق الباقي (178 مفتاحًا) نصوص لم تعد مستخدمة في الكود — يعلّمها Xcode `stale` وتبقى في الملف حتى
> تُنظَّف. أي شاشة جديدة يجب أن تُضاف نصوصها للكتالوج بالعشر لغات.

> **درس من دفعة الترجمة:** أخطر خطأ هنا ليس النص الناقص بل النص **في غير لغته** — إزاحة صف واحد في دفعة
> تُسند الفرنسية للإسبانية والروسية للأردية. هذا يبني بنجاح ويمر من كل اختبار، ولا يراه إلا قارئ تلك اللغة.
> لذلك يحرسه الآن `LocalizationIntegrityTests` بفحص **نظام الكتابة** لكل لغة (سيريلية · ديفاناغارية ·
> عربية · هان)، مع قائمة استثناء لأسماء العَلَم التي تبقى لاتينية عمدًا.

> **تنبيه سابق أُصلح:** كان 39 مفتاحًا يحمل النص الإنجليزي منسوخًا حرفيًا في الروسية والهندية والأردية
> والصينية ومعلَّمًا `translated` — أي ترجمة زائفة تُظهر الإنجليزية لمن لا يقرأها. تُرجمت فعليًا.

مصطلحات البلوت (`Sun`، `Hokum`، `Coffee`) تبقى كأسماء عَلَم في كل اللغات، مثل `trump` في البريدج.

### كيف يُترجَم محتوى الكتالوج

المحتوى يُزرع في SwiftData **مرة واحدة** عند أول تشغيل، لذا ترجمته وقت الزرع كانت ستُجمّده على لغة أول
تشغيل. بدل ذلك يبقى النص العربي مخزَّنًا كـ**مفتاح ترجمة**، ويُترجَم **وقت العرض** عبر خصائص محسوبة
(`displayTitle` / `displayDescription` / `displayPlayerCount` / `displayDuration` في `GameCatalogItem`،
و`displayTitle` / `displayBody` في `GameRuleSection`). النتيجة: المحتوى يتبع لغة الجهاز فورًا عند تغييرها.

> **مهم عند إضافة لعبة جديدة:** استخدم خصائص `display*` في الواجهات ولا تقرأ الحقول المخزَّنة مباشرة،
> وإلا ظهر المحتوى بالعربية دائمًا.

## البناء والنشر (Xcode Cloud)

**يجب البناء عبر Xcode Cloud وليس محليًا.** أبل ترفض أي بناء بـSDK أقدم من المطلوب حاليًا برسالة
`ITMS-90111: Unsupported SDK or Xcode version`، وأحدث Xcode مستقرة (26.6 / SDK 26.5) لم تَعُد كافية،
بينما نسخ البيتا مرفوضة للإرسال (تُقبل للرفع فقط). Xcode Cloud يبني دائمًا بأدوات أبل المعتمدة لحظيًا.

سكربت `ci_scripts/ci_post_clone.sh` يطبع نسخة Xcode والـSDK في سجل البناء ويتحقق من وجود حزمة
`BalootEngine` المحلية قبل المتابعة.

## سياسة التجارة

النسخة الحالية مجانية بالكامل: لا يوجد Paywall، ولا ملف StoreKit، ولا منتجات شراء داخل التطبيق مضمّنة في
البناء. إذا تقرر إضافة منتج شراء مستقبلًا، يجب تجهيز المنتج وبياناته ولقطة مراجعة IAP في App Store Connect
وإرساله مع إصدار جديد قبل إضافة أي مراجع له داخل التطبيق.

## المتطلبات

- Xcode 16 أو أحدث (تم التطوير والاختبار على Xcode 26.4.1 / Swift 6.3.1).
- iOS 17.0 فأعلى. **التطبيق يستهدف الآيفون والآيباد معًا** (`TARGETED_DEVICE_FAMILY = "1,2"`) مع دعم
  الاتجاهات الأربعة على iPad وتعدد المهام (أُزيل `UIRequiresFullScreen`). الآيفون يبقى رأسيًا كما كان.
  رُوجعت الشاشات فعليًا على محاكي iPad في الوضعين الرأسي والأفقي (انظر «التحقق البصري» أدناه).
- لا حاجة لأي حساب أو مفتاح API أو اتصال شبكة لتشغيل التطبيق نفسه.
- للتوقيع والأرشفة الفعلية (Archive) على جهاز حقيقي أو للرفع إلى App Store Connect: حساب Apple Developer
  Program فعّال. `DEVELOPMENT_TEAM` في المشروع مضبوط مسبقًا على Team ID الخاص بالمالك (`4HM66AD594`)،
  و`CODE_SIGN_STYLE = Automatic`.

## التشغيل في Xcode

```bash
open BalootHub.xcodeproj
```

1. اختر Scheme باسم **BalootHub** ومحاكي iPhone (مثل iPhone 17).
2. شغّل بـ ⌘R، أو نفّذ الاختبارات بـ ⌘U.
3. عند أول تشغيل، يُزرع كتالوج الألعاب تلقائيًا داخل قاعدة بيانات SwiftData محلية على الجهاز.

من سطر الأوامر:

```bash
xcodebuild build -scheme "BalootHub" -destination "platform=iOS Simulator,name=iPhone 17"
xcodebuild test  -scheme "BalootHub" -destination "platform=iOS Simulator,name=iPhone 17"
```

اختبارات محرك البلوت (حزمة Swift مستقلة، لا تحتاج Xcode):

```bash
cd Packages/BalootEngine && swift test
```

## Xcode Cloud

يحتوي المستودع مجلد [`ci_scripts/`](ci_scripts/) بجانب `BalootHub.xcodeproj` مباشرة (المكان الذي يشترطه Apple).
السكربت الوحيد حاليًا هو `ci_post_clone.sh`: يعمل بعد استنساخ المستودع وقبل حل اعتماديات SPM، ويسجّل نسخة
Xcode/Swift المستخدمة في بيئة البناء السحابية، ويتحقق من وجود حزمة `Packages/BalootEngine` قبل المتابعة حتى
تظهر أي مشكلة بنية بوضوح في السجلّ بدل فشل غامض لاحقًا. لم تُضف سكربتات `ci_pre_xcodebuild.sh` أو
`ci_post_xcodebuild.sh` لأنه لا يوجد لهما عمل فعلي بعد (لا تنبيهات خارجية ولا خطوات ما بعد بناء مطلوبة حاليًا).

تفعيل Xcode Cloud نفسه (Product → Xcode Cloud → Create Workflow) خطوة تفاعلية داخل Xcode تتطلب حساب Apple
Developer الخاص بك، ولا يمكن لأداة آلية أن تقوم بها نيابة عنك — هذا موثّق رسميًا من Apple نفسها: "Get
started by configuring a workflow **in Xcode**" ([developer.apple.com/xcode-cloud/get-started](https://developer.apple.com/xcode-cloud/get-started/)).
لا يوجد مسار بديل عبر الويب لإنشاء أول Workflow لمنتج جديد لم يُربط بـ Xcode Cloud من قبل.

## GitHub Actions (بديل فوري يعمل الآن)

بما أن Xcode Cloud يحتاج خطوة تفاعلية داخل Xcode نفسه، أُضيف [`ci.yml`](.github/workflows/ci.yml) يشغّل
تلقائيًا عند كل `push`/`pull request` على `main`:

1. `swift test` لحزمة `Packages/BalootEngine`.
2. `xcodebuild build` ثم `xcodebuild test` لتطبيق `BalootHub` كاملًا على محاكي آيفون متاح تلقائيًا على عامل
   macOS من GitHub.

يعمل هذا فورًا بمجرد الدفع لـ GitHub دون أي إعداد إضافي أو حساب Apple Developer، لكن ملاحظة: عوامل GitHub
قد تحتوي إصدار Xcode مستقر أحدث قليلًا أو أقدم من نسخة البيتا 26 المثبتة على جهازك محليًا — هذا متوقع
وطبيعي في أي CI.

│   └── Tests/BalootEngineTests/ اختبارات المحرك (Swift Testing)

هذه البنية أقرب ما يمكن لما طُلب في BLUEPRINT الأصلي، مع تبسيط بسيط: منطق البلوت (الأوراق/القواعد/الاحتساب/اللاعب
الآلي) وُضع في حزمة Swift محلية مستقلة (`Packages/BalootEngine`) بدل مجلد `GameEngine/` داخل هدف التطبيق مباشرة،
لأن ذلك يجعله:
- قابلاً للاختبار عبر `swift test` دون الحاجة لبناء تطبيق iOS كامل أو محاكي.
- معزولاً فعليًا عن SwiftUI (لا يستورد أي شيء من `SwiftUI` أو `SwiftData`)، وهو ما طلبته التعليمات صراحة.
- جاهزًا لإعادة استخدامه لاحقًا في خادم أو محرك لعب جماعي دون أي تغيير.

## إضافة لعبة أو نمط جديد إلى الكتالوج

كل بطاقات الرئيسية والألعاب تُبنى من نموذج بيانات واحد (`GameCatalogItem` + `GameRuleSection`) دون أي شرط
`if`/`switch` خاص بكل لعبة في الشاشات نفسها. لإضافة لعبة جديدة:

1. افتح [`CatalogSeeder.swift`](BalootHub/Core/Persistence/CatalogSeeder.swift).
2. أضف عنصر `GameDefinition` جديدًا في `allDefinitions` (الاسم، التصنيف، الوصف، عدد اللاعبين، الصعوبة،
   المدة، الأيقونة، وهل هي قابلة للعب).
3. املأ الأقسام العشرة لقواعد اللعبة (`StandardRuleSectionKind`) بمحتوى عربي أصلي.
4. هذا كل شيء — البطاقة ستظهر تلقائيًا في القسم الصحيح بالرئيسية، وفي شبكة صفحة الألعاب، وفي نتائج البحث
   والفلاتر، وستُبنى صفحة التفاصيل والقواعد الخاصة بها تلقائيًا.

> ملاحظة: الكتالوج يُزرع مرة واحدة فقط عند أول تشغيل (`CatalogSeeder.seedIfNeeded`). لرؤية عناصر جديدة أثناء
> التطوير، احذف التطبيق من المحاكي أولًا لمسح قاعدة البيانات المحلية القديمة.

## تصنيف المحتوى

- **ألعاب البلوت**: بلوت كلاسيكي، بلوت صن، بلوت حكم، بلوت مشاريع، بلوت دبل، بلوت أشكال، قهوة وقفل الحكم،
  وبلوت كبوت — هذه كلها أنماط/قواعد ضمن لعبة البلوت نفسها، وليست ألعابًا منفصلة.
- **أدوات البلوت**: بلوت تدريب، تحدي حساب النقاط، تسجيل البلوت، دليل مزايدة البلوت، كتالوج مشاريع البلوت،
  ودليل اللعب الجماعي والسوالف —
  أدوات مساعدة، ليست جولات لعب تنافسية.
- **ألعاب ورق أخرى**: كوت بو ستة، طرنيب، تركس، هاند — ألعاب ورق شعبية مستقلة تمامًا عن البلوت.

## قواعد البلوت الافتراضية المستخدمة في المحرك

بعض تفاصيل قواعد البلوت مختلف عليها بين المجالس، فاختار هذا التطبيق إعدادًا افتراضيًا موثّقًا وقابلاً للتهيئة
عبر `BalootRulesConfiguration` (محرك اللعب) و`ScoreRules`/`ScoreRulePreset` (مسجّل النقاط):

| القاعدة | الافتراضي المستخدم |
|---|---|
| ترتيب أوراق نمط حكم (نوع الحكم) | الشايب (J) أعلى، ثم 9، A، 10، K، Q، 8، 7 |
| ترتيب أوراق نمط حكم (الأنواع الأخرى) ونمط صن | A أعلى، ثم 10، K، Q، J، 9، 8، 7 |
| مجموع نقاط جولة حكم | 162 (152 من الأوراق + 10 لآخر أكلة) |
| مجموع نقاط جولة صن الأساسي | 130 (120 من الأوراق + 10 لآخر أكلة) |
| مضاعف احتساب صن ضمن هدف المباراة | ×2 (فتصبح 260) — `sunScoreMultiplier` |
| الإلزام بالقطع بالحكم عند عدم توفر النوع | مفعّل افتراضيًا — `mustTrumpWhenVoid` |
| الإلزام بالتعلية (حكم أعلى من المطروح) | غير مفعّل افتراضيًا — `mustOvertrump` |
| أسلوب المزايدة | دورة كاملة (`BiddingStyle.full`): 5 أوراق + ورقة مكشوفة، جولة أولى، جولة أشكال، مضاعفة، ثم 3 أوراق |
| «صن فوق حكم» | مفعّل: يجوز شراء الصن فوق الحكم في نفس الجولة، ولا يُشترى فوق الصن |
| مرور الأربعة في الجولتين | دورة ميتة بلا نقاط لأي فريق مع انتقال الموزّع |
| المشاريع المعتمدة في المحرك | البلوت 20 · سرا 20 · خمسين 50 · مية 100 (تسلسل خماسي أو أربع من نفس القيمة) · أربعمية 400 |
| المفاضلة بين المشاريع | صاحب أقوى مشروع يأخذ كل مشاريعه والخصم لا شيء؛ البلوت مستثنى ويُحتسب دائمًا |
| توقيت الإعلان | مرحلة `declaring` مستقلة قبل أول ورقة — `projectsRequireDeclaration` |
| المضاعفات داخل اللعب | دبل ×2 · ثري ×3 · فور ×4 · قهوة ×6، مع «قفل» لإنهاء التصعيد |
| الكبوت (أخذ الأكلات الثماني) | +26 في الحكم و+44 في الصن — `kabootBonusHokum` / `kabootBonusSun` |
| طياح المشتري | مفعّل: إن لم يتجاوز المشتري خصمه ذهبت كل نقاط الجولة للخصم — `declarerMustWinMajority` |
| مضاعفات تسجيل البلوت (دبل/ثري/فور) | ×2 / ×3 / ×4 افتراضيًا — Preset "الصيغة القياسية" |
| مضاعف "قهوة" | ×4، ومعطّل افتراضيًا حتى يُفعَّل من الإعدادات |
| الحد المستهدف الافتراضي لجلسة التسجيل | 152 نقطة، وقابل للتخصيص لكل جلسة |

## الاختلافات القابلة للتهيئة

- **`BalootRulesConfiguration`** (`Packages/BalootEngine/Sources/BalootEngine/Rules/`): مجموع نقاط حكم/صن،
  مكافأة آخر أكلة، الإلزام بالقطع، الإلزام بالتعلية، أسلوب المزايدة، تفعيل كل نوع مشروع ونقاطه، معاملات
  المضاعفات وسقفها والقفل، مكافأة الكبوت، وقاعدة طياح المشتري. فك الترميز فيها **متسامح**: أي إعداد يُضاف
  لاحقًا يأخذ قيمته الافتراضية بدل إفشال «قواعد مجلسي» المحفوظة سابقًا.
- **`AIProfile`** (`Packages/BalootEngine/Sources/BalootEngine/AI/`): خمسة مستويات (مبتدئ · عادي · محترف ·
  خبير · شيخ البلوت) وسبع شخصيات (متوازن · محافظ · هجومي · متخصص حكم · متخصص صن · مخاطر · دفاعي). الاختلاف
  بينها في **عمق التحليل ومعاملات القرار** لا في أخطاء عشوائية: المبتدئ لا يتتبع الأوراق الخارجة، والمحترف
  فما فوق يحاكي توزيعات محتملة بعدد عيّنات متصاعد.
- **`ScoreRules` / `ScoreRulePreset`** (`BalootHub/Domain/Services/ScoreRules.swift`): عاملا الدبل/الثري/الفور،
  عامل القهوة، وهل القهوة مفعّلة أصلًا — تُختار من شاشة الإعدادات ولا تُثبَّت داخل أي View.
- **`AppSettings`**: الحد المستهدف الافتراضي، تفعيل القهوة، التأكيد قبل الحذف/التراجع، المظهر، الصوت،
  الاهتزاز، **وخيارات تخصيص الطاولة** (شكل الورقة وظهرها ولبس الطاولة والخلفية والأفاتار والثيم ومؤثرات
  الاحتفال). الخيارات الجديدة أُضيفت بقيم افتراضية مضمّنة في تعريف الخاصية لا في المُهيّئ فقط، حتى تمرّ
  ترقية SwiftData التلقائية على قواعد البيانات الموجودة مسبقًا.
- **`AppearanceCatalog`** (`BalootHub/Domain/Services/`): يقرر أي نمط مفتوح حسب ``CareerRank``. الفتح
  **بالتقدّم فقط** — لا يوجد أي مسار شراء — ويرفض `apply(entry:to:)` صراحةً أي نمط مقفول بدل تطبيقه بصمت.
  أي نمط محفوظ ثم صار مقفولًا (بعد حذف سجل المباريات مثلًا) يرتد لقيمته الافتراضية بدل أن تعلق الشاشة.

## الاختبارات المنفذة فعليًا

- **`Packages/BalootEngine/Tests/BalootEngineTests`**: اختبارات لمحرك البلوت، المزايدة، المشاريع، التحليل،
  Replay، Sandbox، وما يرتبط بحتمية القواعد.
- **`BalootHubTests`**: اختبارات للتطبيق، التسجيل، الكتالوج، الشراء، الأكاديمية، التحديات، الإحصائيات،
  مشاركة المواقف، ومدرب "وش تلعب؟".

لا تثبّت الوثائق رقمًا إجماليًا للاختبارات لأن العدد يتغير مع كل دفعة تطوير؛ المصدر المعتمد هو تشغيل
`swift test` لحزمة المحرك و`xcodebuild test` للتطبيق.

## البيانات المحلية المستخدمة (خصوصية)

كل البيانات تُخزَّن محليًا على الجهاز فقط عبر SwiftData، ولا تُرسَل لأي خادم:

- كتالوج الألعاب وحالة المفضلة لكل لعبة.
- جلسات تسجيل البلوت وجولاتها (أسماء الفرق، النقاط، المشاريع، المضاعفات، الملاحظات، التواريخ).
- إعدادات التطبيق (المظهر، الصوت، الاهتزاز، الحد المستهدف، صيغة المضاعفات، تأكيد الحذف).

لا يطلب التطبيق أي صلاحية للوصول للصور أو جهات الاتصال أو الموقع، ولا يحتوي أي SDK تحليلات أو تتبّع، ولا
يفتح أي اتصال شبكة.

**بيان الخصوصية**: `BalootHub/Resources/PrivacyInfo.xcprivacy` موجود ومضمَّن في الحزمة. التطبيق يستخدم
`UserDefaults` عبر `@AppStorage` (تقدّم الأكاديمية، التحديات المكتملة، الإنجازات، أفضل سلسلة في تحدي
النقاط)، وهي ضمن **Required Reason APIs**، فيُفصح عنها بالرمز `CA92.1` (قراءة وكتابة بيانات لا يصل إليها
إلا التطبيق نفسه). البيان يعلن كذلك أن التطبيق **لا يتتبّع ولا يجمع أي بيانات**.

> ⚠️ كان هذا الملف **غائبًا**، وكان هذا القسم يدّعي أنه غير مطلوب. الرفع كان سيُرفض بـ
> **ITMS-91053: Missing API declaration** — وهو رفض لا يظهر في أي بناء أو اختبار محلي، بل عند الرفع فقط.
> يحرسه الآن `PrivacyManifestTests`. أي `Required Reason API` جديدة (طوابع الملفات · مساحة القرص · وقت
> الإقلاع · لوحات المفاتيح النشطة) يجب أن تُضاف للبيان **وللاختبار** معًا.

## الميزات غير المكتملة (بصراحة)

- **صفحات الكتالوج المستقلة لمشاريع/دبل/أشكال/قهوة/كبوت**: ما تزال `isPlayable = false` كعناصر كتالوج
  منفصلة، **لكن قواعدها صارت مدعومة فعليًا داخل المحرك** وتظهر أثناء «بلوت كلاسيكي»: جولة الأشكال جزء من
  دورة المزايدة، والدبل/الثري/الفور/القهوة والقفل مطبَّقة في `BiddingEngine`، والكبوت يُكتشف ويُكافأ في
  `ScoreCalculator`، ومشاريع السرا والخمسين والمية والأربعمية مطبَّقة في `ProjectDetector` بمفاضلة كاملة
  بين الفريقين. الناقص هو **تحويل كل نمط إلى وضع لعب مستقل بمدخل خاص به من الكتالوج**، لا القواعد نفسها.
- **تحدي حساب النقاط**: صفحة مرجعية تشرح الاحتساب، وليست اختبارًا تفاعليًا (كويز) فعليًا بعد.
- **بلوت تدريب**: يعيد استخدام قالب صفحة القواعد نفسه بمحتوى تعليمي، وليس شاشة تفاعلية منفصلة بخطوات
  متسلسلة.
- **مدخل اللعب الفعلي**: البلوت قابل للعب من مدخل واحد هو «بلوت كلاسيكي». الصن والحكم ليسا لعبتين
  منفصلتين؛ يبدآن كخيارات شراء داخل دورة المزايدة الكاملة بين اللاعبين الأربعة، ثم يثبت المحرك النمط ولون
  الحكم بعد الشراء.
- **اللعب الجماعي عن بعد والمايك/السوالف**: غير مضاف كميزة Online في هذا الإصدار. الموجود الآن هو لعب ضد
  الذكاء ولعب أربعة أشخاص على نفس الجهاز. إضافة الصوت والغرف تحتاج Game Center/CloudKit أو خادم غرف، صلاحية
  ميكروفون، سياسة خصوصية محدثة، واختبارات انقطاع/إعادة اتصال قبل إرسالها للمراجعة. **البنية جُهّزت لها**:
  `MatchTransport` يفصل المحرك عن وسيلة النقل، و`SpectatorFeed` يحجب الأيدي بحذفها من اللقطة لا بإخفائها
  بصريًا، وقائمة `MultiplayerReadiness` تُعرض داخل الإعدادات وتفصل ما جهُز عمّا يبقى مطلوبًا.
- **Strict Concurrency**: مفعّلة بالكامل (Swift 6 Language Mode) في حزمة `BalootEngine` **وفي هدف التطبيق
  أيضًا** (`SWIFT_VERSION = 6.0` في كل التهيئات). كان هذا الملف يقول سابقًا إن هدف التطبيق يبني بوضع
  Swift 5، وهو غير صحيح.

  > ⚠️ **فخ تُوُقِّع فيه فعلًا:** عامل GitHub (`macos-15`) يحمل **Xcode 16.4**، والتطوير المحلي على 26.6.
  > فحص العزل يختلف بين الإصدارين، فكود يترجم نظيفًا محليًا قد يفشل على CI. حدث ذلك مع
  > `WhatToPlayShareCodeImportResult` الذي كان يحمل نموذج SwiftData ويُرجَع من دالة غير معزولة إلى
  > `MainActor` — بقي `main` أحمر ثلاثة كوميتات بسببه. **نجاح البناء محليًا لا يثبت نجاح CI.**
- **صور/رسومات مخصصة لكل لعبة**: تُستخدم SF Symbols فقط حاليًا بدل رسوم توضيحية أصلية لكل لعبة. أما
  **طاولة البلوت** فصارت قابلة للتخصيص فعليًا (أشكال أوراق، ظهر ورقة، لبس طاولة، خلفية، أفاتار، ثيم) وكلها
  مرسومة بالكود عبر أشكال وتدرّجات SwiftUI بلا أي ملف صورة، فلا تزيد حجم الحزمة.

- **الأصوات**: لا يشحن التطبيق أي ملف صوتي. المؤثرات تستخدم أصوات واجهة النظام مباشرة عبر
  `AudioServicesPlaySystemSound` مع اهتزاز `UIFeedbackGenerator`، وكلاهما يُطفأ من الإعدادات. موسيقى أو
  مؤثرات أصلية تحتاج أصولًا صوتية مرخّصة غير متوفرة الآن.
- **التحقق البصري على المحاكي**: نُفِّذ فعليًا على iPhone 17e وiPad Pro 11 بوصة (رأسي وأفقي) وبأكبر مقاس
  خط وصولية. اللقطات كشفت ثلاثة عيوب لم يكشفها أي اختبار آلي، وأُصلحت كلها:
  1. نصوص الشريط العلوي وأسماء المقاعد كانت بألوان مصمَّمة لخلفية فاتحة فصارت باهتة فوق لبس الطاولة الداكن.
  2. سطر تعليمات المزايدة كان يُقصّ على عرض الآيفون (`fixedSize` أصلحه).
  3. **الأخطر:** عند أكبر مقاس خط وصولية كانت أزرار «صن/حكم/بس» تُدفع خارج الشاشة بلا وسيلة للوصول إليها —
     أي أن اللاعب لا يستطيع المزايدة إطلاقًا. صار التخطيط يتحوّل إلى تمرير رأسي كامل عند تلك المقاسات.

  > للتحقق البصري السريع: `xcrun simctl launch <device> app.balooThub.ios -BalootHubStartRoute balootGamePlay`
  > (وسيط Debug فقط، يفتح شاشة عميقة مباشرة بدل التنقل اليدوي إليها).

- **تخطيط طاولة اللعب على iPad**: المقاعد الأربعة موزّعة حول الطاولة (شمال أعلى · غرب وشرق على الجانبين ·
  يدك أسفل متوسّطة)، والآيفون يحتفظ بتخطيطه الضيّق. ما يزال ناقصًا: رسوم أوراق أصلية بدل SF Symbols.

- **مفاتيح الترجمة المهجورة**: يوجد نحو 235 مفتاحًا لا يظهر حرفيًا في الكود، **ولا يجوز حذفها جملةً**.
  فحصها أثبت أن 23 منها مفاتيح تنسيق تولّدها SwiftUI وقت التشغيل من الاستيفاء النصي (`%@ %@` ·
  `%@ ضد %@` · `%lld أوراق`)، و165 أخرى تظهر كأجزاء من نصوص أطول. حذفها يفقد ترجمات مستخدمة فعلًا،
  والخسارة **لا تظهر في أي اختبار** — تظهر فقط لمستخدم يقرأ بتلك اللغة. الفائدة (حجم ملف) لا توازن الخطر.
